# פרויקט ניהול פקודות מסחר - שלב ב'

מערכת לניהול תיק השקעות ופקודות מסחר, המשלבת מודלים מונחי עצמים (שלב א') יחד עם תקשורת רשת, עיבוד מקבילי ואסינכרוני (שלב ב').

**מגישים:**
* נועם פרץ
* אלירן דוש
* דביר דור

---

### 1. מה נוסף בשלב 2?
בשלב זה המערכת הורחבה ממשחק נתונים מקומי למערכת הפועלת מול העולם האמיתי ומעבדת נתונים במקביל:
* **תקשורת רשת:** הוספת מודול (`api_client.py`) למשיכת שערי מניות עדכניים מ-Yahoo Finance באמצעות ספריית `requests`.
* **עיבוד אסינכרוני:** שילוב `asyncio` לאיסוף סטטוסים של מספר פקודות במקביל, כדי לייעל משמעותית את זמן ההמתנה בפניות קלט/פלט (I/O).
* **מקביליות ובטיחות הליכים:** שימוש ב-`threading.Lock` לשריון תקציב מול היתרה בתיק, כדי לאפשר למספר תהליכונים לפעול במקביל ללא התנגשויות (Race Conditions).

### 2. איך מריצים?
* **דרישות סביבה:** Python 3.10 ומעלה.
* **התקנה:** התקנת התלויות מתבצעת מתוך קובץ ה-`pyproject.toml` על ידי הרצת הפקודה: `pip install requests pytest pytest-asyncio python-bidi` (ללא סודות או משתני סביבה מיוחדים).
* **הרצת המערכת ללא רשת (מידע מדומה כברירת מחדל):** 
  `python main.py`
* **הרצת המערכת מול שירות אמיתי ברשת:** 
  `python main.py --online`
* **הרצת חבילת הבדיקות (Tests):**
  `python -m pytest`

### 3. איך הקוד מאורגן?
הקוד מחולק בצורה מודולרית לפי עקרונות תכנון נכון (Separation of Concerns):
* **`main.py`:** המודול המרכזי בתיקיית השורש, המשמש כנקודת הכניסה וההדגמה של המערכת.
* **תיקיית `project_name/` (תת-המערכת המרכזית):** מכילה את לוגיקת הליבה.
  * `models.py`: הגדרת מחלקות הנתונים (Portfolio, MarketOrder).
  * `services.py` & `strategies.py`: לוגיקה עסקית, בקרת תקציב ופולימורפיזם של אישורי פקודות.
  * `api_client.py`: אחריות בלעדית על תקשורת ה-HTTP החיצונית וטיפול בשגיאות רשת.
  * `async_processing.py`: ניהול משימות מקביליות.
* **תיקיית `tests/`:** מכילה את קבצי בדיקות היחידה (Unit Tests), מופרדים לחלוטין מקוד הייצור.

### 4. החלטות תכנון מרכזיות
* **שירות חיצוני וטיפול בכשלים:** בחרנו ב-Yahoo Finance כמקור נתונים. התקשורת מנוהלת תוך שימוש במנגנון חריגות (Exceptions), כך שבמקרה של כשל ברשת או טיימאאוט, המערכת לא קורסת אלא מציגה הודעת שגיאה ועוברת למחיר גיבוי מדומה (Fallback).
* **תבניות תכנון:** השתמשנו ב-Dependency Injection במחלקת `OrderApprovalService` כדי להזריק לה מדיניות אישור (Policy) שונה בכל פעם, מה שמאפשר גמישות וניתוק תלויות.
* **ניהול משאב משותף (Lock):** כאשר מספר תהליכונים מנסים לאשר פקודות מול אותו תיק השקעות (`Portfolio`), היתרה היא משאב משותף. הוספנו מנעול (`Lock`) כדי למנוע מצב של שריון כפול (Race Condition), כך שכל תהליכון ניגש לעדכון היתרה בתורו תוך הבטחת שלמות הנתונים (Thread Safety).
* **הפרדה ולבדיקה (Testability):** הקוד תוכנן כך שניתן "לזייף" (Mock) את פונקציית התקשורת או את שערי ההמרה במהלך הבדיקות האוטומטיות, ללא תלות ברשת זמינה.

### 5. הוכחות שהמערכת עובדת
המערכת פותחה תוך שימוש במתודולוגיית TDD (Red, Green, Refactor). 
הפרויקט כולל מערך בדיקות מקיף (40 בדיקות אוטומטיות ב-`pytest`) המכסה את כל הרכיבים:
* מודלים תקינים ולוגיקה עסקית.
* סימולציות של תקשורת רשת והתאוששות משגיאות.
* בדיקות אסינכרוניות לווידוא איסוף נתונים מקבילי תקין.
כל הבדיקות רצות ועוברות בהצלחה (100% Passed). בנוסף, העבודה נוהלה בגרסאות באמצעות מחויבויות (Commits) מסודרות למאגר ב-GitHub.
